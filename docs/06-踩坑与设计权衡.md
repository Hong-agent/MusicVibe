# 06 · 踩坑与设计权衡

本文记录开发过程中**真实遇到**的问题与最终结论。每一条都对应一次实际调试，极具参考价值。

---

## 坑 1：设备不支持触觉音频通道

**尝试**：最初的思路是用 Android 12+ 的"触觉音频通道"（`CHANNEL_OUT_HAPTIC_A` / `AudioTrack` 触觉播放），理论上可让马达直接"播放"音频波形，保真度最高。

**结果**：测试机（小米 25102RKBEC，Android 16）**不支持**触觉声道，`HapticGenerator.isAvailable()` 返回 false。

**结论**：
- 触觉音频通道理想但**兼容性差**，很多机型没实现；
- **回退方案**：用 `VibrationEffect.createWaveform/createOneShot` 驱动马达，虽然只能控制振幅+时长，但兼容性最好；
- 本项目最终采用纯 Vibrator 方案。

---

## 坑 2：参数变更导致"完全不震动"

**现象**：用户拖动频段滑块后，应用突然**一点不震了**。日志显示"参数已更新并立即生效"每 20ms 刷屏。

**根因**：
每次参数变化都调用 `fc.rebuild()`，而它把**滤波器状态全部清零**（`lx1=lx2=...=0`）。滤波器每 20ms 就从零状态重启一次，**永远无法收敛**，输出恒为 ≈0。

```
参数变化 → rebuild(resetState=true) → 状态清零 → 滤波器从头开始
   ↑                                                    │
   └──────── 用户还在拖动，20ms 后又变化 ←──────────────┘
```

**修复**：把 `rebuild` 拆成两个入口：

```java
void rebuild(HapticProfile p)              { rebuild(p, true);  }  // 仅首次启动
void rebuild(HapticProfile p, boolean reset) { ... if (reset) 清零; }
```

- **首次启动**：`resetState = true`（历史本来就是 0）；
- **运行时调参**：`resetState = false`，**只换系数，保留状态**。

**结论**：这是本项目最关键的教训。任何"可实时调参的 IIR 滤波器"都必须区分"改系数"和"清状态"。

## 坑 3：双重截断导致断续

**现象**：修好"完全不震动"后，震动忽有忽无、断断续续。

**根因**：**两处截断打架**：
1. 服务里 `if (amp > 1000) amp = 1000`；
2. 驱动器里又有 `门槛` 过滤 + 0..255 映射。

AGC 把信号顶到 1000 附近后，服务截断使 `amp` 固定在 1000 附近不动；而 AGC 的再归一化又让 `amp` 在门槛（316）上下抖动——**在"饱和"和"跌回门槛被 cancel"之间反复横跳**。

**修复**：
- **服务不再截断**（只保证 `amp >= 0`），输出可能 >1000；
- **驱动器统一处理**：入口先安全夹取 0..1000，再做门槛过滤与映射。

**结论**：**阈值逻辑必须集中在一层**。分散在两处必然产生难以调试的交互 bug。

## 坑 4：细腻模式（分段波形）失败

**尝试**：为了让振动"更细腻"，实现了一个"分段波形引擎"——把短时能量拆成多段，用 `createWaveform` 下发。

**现象**："感觉很乱"。三重问题：
1. 每 10ms 块触发一次波形，但波形只有 3 段 × 4ms = 12ms，**相邻块相互抵消**；
2. 4ms 分段与 10ms 块长**不整除**，产生漂移；
3. 每块独立 AGC 导致**增益跳变**。

**修复尝试**（累积缓冲 + 滑动峰值 + 30ms 刷新）后仍不理想。

**最终结论**：**删除细腻模式**，回到"单振幅 oneShot + 变更重发"的简单模型。

**教训**：不要在 10ms 的实时块里做复杂波形拼接。"简单可靠"胜过"看似高级"。

---

## 坑 5：延迟过高，与声音不匹配

**现象**："延迟太高了和声音不匹配"。

**根因**：采集环形缓冲取 `minBuf × 2`（约 180ms），读数块 2048 帧（约 43ms），累计延迟 200ms+。

**修复**（详见 [04] §3）：
- 缓冲 `minBuf × 2` → `minBuf × 1`；
- 读数块 2048 帧 → 480 帧（10ms）；
- 增加"脉宽随频率缩短"。

**结论**：**缓冲和块大小是延迟的第一来源**，优先优化这两处。

---

## 坑 6：宽频支路的失败实验

**尝试**：为增加"细节"，加了一条"宽频支路"（完整信号带通后叠加到谐波支路），上限一度提到 24kHz。

**结果**：新版无上限说明，但实测发现高频成分让振动"浑浊"，且与低频谐波叠加后难以调参。

**结论**：**再次删除宽频支路**，只保留单一的谐波链。频宽上限最终收敛到 1150Hz（早期曾用 850~1150 与 400~4000）。

**教训**：**信号链越短越可控**。每加一条支路，调参维度与相互干扰都指数上升。

---

## 坑 7："多了很多无用的震动"

**现象**：引入 AGC 后，用户反馈"多了很多无用的震动"——背景/伴奏/残响都在震。

**根因**（用真实诊断日志定位）：gamma 用了 `< 1` 的指数（当时 0.75），**抬升**了弱信号。实测：

| 内容 | rms | norm | amp | 该不该震 |
|---|---|---|---|---|
| 鼓点 | 0.018 | 1.0 | 1200 | ✅ |
| 伴奏 | 0.0075 | 0.48 | **370~470** | ❌ 却震了 |
| 安静 | 0.0055 | 0.32 | 192 | ✅ 不震 |

**修复**：
- `AMP_GAMMA` 从 0.75 改为 **2.2**（`<1` 抬升 → `>1` 压低）；
- `AGC_RELEASE` 从 0.02 降到 **0.004**（峰值基准更稳，安静段不被重新放大）。

修复后 `norm=0.5` 的伴奏 → `amp≈240`，**低于门槛，不震**。

**结论**：**AGC 已经把动态拉满，gamma 必须用 >1 来"收紧"而非"放宽"**。这是最反直觉、也最重要的一条。

---

## 坑 8：诊断日志是最好的工具

在整个调试过程中，**临时加诊断日志**（打印 `rms / env / agcPeak / norm / amp / pulse`）起了决定性作用。

- 不靠猜：把每一块的中间量打出来，问题一目了然；
- 定量：能精确算出"某个 norm 对应哪个 amp"；
- 可验证：改完参数，用日志确认弱段确实落到门槛之下。

**结论**：调试实时信号处理，**先加日志、用数据说话**，不要凭感觉反复改常数。

> 建议保留一个 `if (DEBUG)` 开关的诊断日志路径，方便后续调参。

## 设计权衡总结

| 议题 | 选择 | 理由 |
|---|---|---|
| 触觉音频通道 vs Vibrator | **Vibrator** | 兼容性优先 |
| 单声道 vs 立体声混音 | **取右声道** | 省算力、避免相位相消 |
| 谐波增强 vs 直接振幅 | **全波整流谐波** | 手机喇叭放不出低频 |
| 固定增益 vs AGC | **AGC** | 跨音源音量鲁棒 |
| gamma <1 vs >1 | **>1** | 消除杂散震动 |
| 细腻波形 vs 单振幅 | **单振幅** | 简单可靠 |
| 多支路 vs 单链 | **单链** | 可控、易调参 |
| 阈值分散 vs 集中 | **集中在驱动器** | 避免交互 bug |

---

## 一句话给后来者

> **信号链要短，阈值要集中，AGC 之后用 >1 的 gamma，参数变更绝不清滤波器状态。**
